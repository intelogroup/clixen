## User prompt spec (SCARF) — apply on every task
User prompts are often terse/vague ("verify X", "why is Y failing?"). Forge the missing
fields yourself before acting: **S**cope (exact file/log/DB/window), **C**ondition
(explicit pass/fail), **A**rtifact (file(s) touched), **R**eport (declared output shape),
**F**ence (what you will NOT touch). Vague verb → state the concrete condition back before
acting. Debug prompt → root cause with evidence FIRST, fix second, no service restarts as
a "fix". One-word prompts (`yes`/`fix`/`next`) after a multi-step plan usually mean a prior
deliverable wasn't produced — check the last Report before treating it as new work.

- Skill matching internals (2026-08-04, `skills_hub.py` `_score_skill`): the file-family tools (read/write/delete/search) dominate ANY query containing "file" because (a) the `files` domain anchor regex `\b(files?|folders?|...|read|open|...)\b` fires +3.0, and (b) each trigger keyword shares a token with the query → +0.5 per keyword (token-overlap branch, line ~331). New skills that operate on files but use category "Docs" lose to them — category "Docs" only matches the `docs` domain regex (`document|pdf|docx|convert|...`), NOT the `files` regex, and the anchor maps `docs`→`documents` but the check is `category_lower == domain or category_lower == mapped`, so category literally "Docs" matches the domain NAME. Fix for a doc-skill that must win "file"-queries: keep category "Docs" and add keyword mass (file/excel/word-bearing keywords, each +0.5), don't switch category to "files" (that silently drops the +3.0 docs anchor on pdf/docx queries). Also: bare-verb keywords ("fix", "check") are leakage traps — any keyword sharing a single generic token lends +0.5 to unrelated queries ("fix my laptop" → repair skill at 1.3). Use multi-word intent keywords ("unreadable content", "docx won't open") for substring +2.0 hits and avoid generic single-verb compounds. Eval method that works: drive `match_skill_for_task` directly on a 5-TP/5-TN case set per skill and iterate keyword sets against a 0.3+0.5-scoring mental model — beats guessing. `test_skills_hub._reset_and_rescan` was also permanently wiping builtin skills_data skills (SKILLS.clear() without restoring) — that's why `test_skills_hub.py`+`test_skills_can_run.py` failed 10 combined but passed separately; fix preserves builtins across the rescan.
- Ringback SIP debugging (2026-08-11): the MCP tool's `[NO ANSWER]` result string is misleading — it fires on ANY non-connect outcome, including a hard SIP `403 Forbidden`/`404 Not Found`, not just an unanswered ring. Always confirm via `docker logs <ringback-container-id> 2>&1 | grep -A3 "Response msg [0-9]*/\(REGISTER\|INVITE\)"` before trusting the tool's text. Root cause found this session: `voice.docker.env`'s `VOICE_SIP_PASS` was stale (account password had been reset in the Linphone dashboard) — Flexisip challenges with 401, client answers with a correctly-formed digest response, but wrong password gets 403 (not a second 401) on both REGISTER and INVITE, which looks identical to "call rejected" until you diff a REGISTER attempt. Separately, `VOICE_SIP_CALLEE=sip:claudecalls@sip.linphone.org` doesn't exist server-side (clean 404 once auth was fixed) — that account was never provisioned; callee swapped to self (`intelogroup`) as a workaround. Self-calling has its own footgun: `voice_agent.py:660`'s comment "do NOT register (avoids self-call fork)" is load-bearing — if `VOICE_SIP_REGISTER` (new opt-in env flag, added this session, default off) is ever enabled even temporarily, Flexisip keeps that registration binding server-side for its full expiry (~1hr) independent of the local container's lifecycle. Any self-call placed while that stray binding is still live gets forked to both your phone AND the leftover pjsua binding — `voice_agent.py` has no `onIncomingCall` handler, so pjsua2's default behavior answers/loops it near-instantly (200 OK in ~2s, too fast for a human), stealing the call before the phone's push notification ever renders. Symptom looks like "call connected on SIP but nothing rang" — actually the self-fork hijack, not a push/APNs bug. Don't flip `VOICE_SIP_REGISTER=1` for a self-call target, ever; use a genuinely separate account, or wait out the stray binding's expiry.
